### 3.1 DQ-03 / DQ-07：逐表门禁不等于同期完整财务包

当前资产负债表分期完整度为：

| 报告期 | 总行数 | 核心完整行 |
|---|---:|---:|
| 2025-03-31 | 5,127 | 5,127 |
| 2025-06-30 | 3,557 | 0 |
| 2025-09-30 | 3,541 | 0 |
| 2025-12-31 | 3,556 | 0 |
| 2026-03-31 | 3,556 | 0 |

利润表后续期间存在部分“营收 + 归母净利润”行，但同报告期没有完整资产负债表和现金流。这说明逐表最低字段门禁只能防止已知壳形状再次进入，不能证明“一套完整财报已更新” [C001, C015]。

**解除门禁：**重建候选必须在副本/staging 中按 `stock_code + report_date` 求三表交集；缺任一必需表的发行人期间只能标为 incomplete，并从指标发布候选排除。正式发布前对新旧版本生成差异报告并由数据负责人签署。

启动时的“新公告/财报检查”也不能作为反证。`_check_new_announcements` 只返回当前 UTC 时间，没有请求公告源、保存远端检查点或比较公告 ID；它不能发现正式财务数据已落后 [C023]。解除 DQ-07 还必须证明：同一官方披露源检查点可重复运行、不会漏掉更正/重述，并能把新报告导入 staging 验收。

### 3.2 DQ-05：分红监测存在，但错误值仍进入指标

只读证据显示 `announcement_date=0/44,883`，且全部 `ex_date` 仅落在 12-31/06-30。外部规则调查支持以权益分派实施公告及其更正/撤销链作为事件证据，而不是财务期末 [C002, C018]。

计算器仍按 `ex_date` 计算最近分红年、DPS、股息率、分红率和连续分红年数。`DIVIDEND_DATES_UNVERIFIED` 只出现在状态 API，不能阻止这些值进入个股页或筛选 [C012]。

**解除门禁：**在副本中从适用交易所/发行人正式实施公告重建；每条事件保存公告标识、PDF 哈希、披露时间、记录日、除权除息日、支付日、实施状态及更正链。重建前，日期依赖指标必须返回不可用状态或在所有消费面强制显示低置信度，不能仅在状态页报警。

### 3.3 DQ-06：旧 lineage 无效，当前代码也不能重建字段链

全部 15,649 条 `source_audit` 的哈希长度为 0，全部无法关联 `fetch_batch`；字段名主要是 `__price_count__`、`__balance_count__`、`__dividend_count__`。另一方面，133 条 `fetch_batch` 自身有 64 位哈希，但只覆盖一个价格逻辑批次，未被 `source_audit` 引用 [C003]。

源码可写部分 `fetch_batch`，但仓库范围内没有生产 `INSERT INTO source_audit` 路径。个股 API 仍把合成摘要作为字段审计返回，并把 `fetch_time` 别名为 `effective_date` [C013]。

**解除门禁：**建立 source entity -> extraction activity -> mapped field 的可重现链，至少保存原始文件/响应 ID、SHA-256、获取时间、请求参数、映射版本、适用日期、重述版本和字段定位。旧合成摘要需在备份后明确降级为 `synthetic_summary`，不得继续作为字段级证明。

### 3.4 DQ-10：孤儿身份已解释，但覆盖与复发路径未关闭

341 个 raw-only 代码中，328 个属于 BSE；另 13 个并非未知发行人，而是 `001914`、`000561` 等深市代码的未补零重复行。每个未补零代码的 raw 行数与补零代码的 raw/QFQ 行数相同 [C019]。

这只解释身份，不构成删除授权。四个正常化代码仍有 raw/QFQ 范围或行数分裂；增量更新只抓 raw，能够在全量回填通过后再次制造分裂 [C004, C014]。

**解除门禁：**先导出 13 个重复代码并校验逐行内容/哈希，再由数据负责人批准隔离；定位并锁死去零写入源。非豁免代码要求 raw/QFQ 同一批次、同一最新交易日、明确日期交集和失败原因；增量路径也必须满足同一规则或记录阻断性的 deferred-QFQ 状态。

### 3.5 DQ-11：未知状态仍被编码为 false

`stock_meta` 共 5,528 行，申万一级/二级覆盖均为 0，`is_suspended IS NULL` 为 0，`is_suspended=FALSE` 为 5,528。上市日期与现有最早价格日相差不超过 28 天，但尚未经过发行人/交易所外部抽样签署 [C005]。

申万是许可分类法，不应假设完整机器可读数据可以免费再分发。CSRC JR/T 0020-2024 可作为公开的不同分类体系，但不能静默冒充申万。

**解除门禁：**从适用交易所或法定披露取证 ST/停复牌/上市状态并保留未知；为申万取得合法授权，或经产品决策显式迁移到另一命名和版本均不同的分类体系。G19 验收需记录来源、版本和有效日期。

### 3.6 DQ-12 / DQ-14：计算门禁有效，但正式操作状态未治理

正式 SQLite 的 8 条覆写均为 `active` 且未撤销；其中多个同股票/字段/期间冲突。代码只消费 `published`，临时库迁移也会拒绝多个当前 published 版本，但正式 SQLite 尚未应用 v2。4 条筛选记录中有 3 条是结果严格等于 `600519 / name=test` 的验收测试工件，另有 1 条标题为 `test7` 的操作性结果；此外还有 2 条陈旧 running 作业和 0 retry [C006, C007]。

分红回填失败直接计数并跳过，不进入 retry；缺 `ex_date` 的行也直接跳过。该写入逐行使用普通连接而非整个股票/批次事务。内存 DuckDB 故障注入进一步证明：同一股票第二行日期转换失败后，第一行仍保留，但报告记为该股票失败且 `total_rows=0`，即数据状态与任务状态同时失真 [C011]。

通用 retry 也没有形成闭环。隔离执行中，成功抓取 `price_daily` 后唯一副作用是删除 `retry_list` 记录，没有调用 DuckDB 目标写入；现有初始化/回填又会记录 `data_type='price_daily_qfq'`，而 `FetchRequest` 只接受 `price_daily` 并用 `adjust='qfq'` 表示复权类型，因此 QFQ retry 连通用请求边界都无法通过 [C020]。

父任务状态会进一步掩盖这些失败。构造 failed/missing/partial 子步骤后，`run_full_init`、`run_full_backfill` 和 `run_incremental_update` 均返回顶层 `success`；前两者还把该状态写入 `job_logs`。CLI `make_response` 只依据是否显式传入 `error_code` 决定 `result.status='ok'`，所以嵌套 partial 仍被包装成 ok [C021]。

**解除门禁：**只在导出和负责人逐条确认后处理既有筛选/覆写/作业记录；先在副本演练 SQLite v2。为作业增加 heartbeat/abandoned 语义；父状态必须由必需子步骤聚合，CLI/作业日志不得把 partial 记为 success/ok。retry 必须按数据类型调用幂等目标写入，只有提交和后置校验成功后才能删队列；QFQ retry 必须规范化为 `price_daily + adjust=qfq`。对分红批次做故障注入，证明任意中断不发布半批数据。

### 3.7 DQ-13：迁移代码存在，但正式库仍未迁移

当前代码声明 QFQ `turnover_rate`、快照 `calculated_at/data_version`、nullable ST/停牌默认值和 SQLite published 唯一索引。临时库回归证明部分迁移可重复执行，但正式 QFQ 仍没有 `turnover_rate`，正式 SQLite 迁移表只有 v1 [C007]。

**解除门禁：**在正式库副本上执行迁移，验证幂等、行数、主键、双向 schema diff 和 API 行为；经批准、备份和回滚演练后再迁移正式库。当前只读兼容不是 G18 通过证明。

## 4. G22：用户可见性仍未通过

后端 `/api/data-status/summary` 已返回结构化 `data_quality`，包括：

- 记录日期与完整日期；
- 价格日期、快照日期和计算日期；
- 分红占位行、无效 lineage、未发布覆写、running 作业；
- 六个机器可读警告码。

`DataStatusPage.vue` 的类型和模板均未读取 `data_quality`，所以主要状态页只显示总量和表面日期。进一步追踪显示，该问题不是单页遗漏：

- 个股指标 API 返回 `freshness`，但 `StockDetailPage.vue` 不渲染它，仍直接展示陈旧指标和不可信的股息率、分红率、DPS、连续分红年数；
- 筛选引擎允许 `dividend_yield`、`payout_ratio`、`dps` 和 `consecutive_div_years`，页面/导出只带快照 `data_date`，不带质量警告、价格日期、计算日期或置信度；
- CLI `data status` 和 `data diagnose` 只统计覆盖数量，不调用 `build_data_quality_status`；现有 count 非零时甚至可能给出 `healthy=true`。

因此，后端存在警告对象不等于用户已获得风险提示，更不等于不可信值被禁止使用 [C008, C012, C022]。

**G22 通过条件：**建立统一、类型化的质量契约并覆盖状态页、个股页、筛选、CSV 和 CLI。每个消费点必须展示记录日期、完整日期、价格日期、计算日期、数据版本、阻断警告和影响范围；不可信指标必须返回 unavailable/reason code，或在用户显式确认前禁止筛选、排序、保存和导出。完成后用真实浏览器在桌面/窄屏验证文案、可访问性和 API 错误状态，并用 CLI/API 契约测试证明警告不可被遗漏。
