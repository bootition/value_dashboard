# SKILL：硬数字发布

> 适用：任何要写进 `docs/reports/`、`docs/STATUS.md`、`docs/runbooks/ops-knowledge-base.md` 的
> **精确数字**——行数、期数、只数、覆盖率、阈值、迁移版本号、通过用例数。
>
> 不适用：量级描述（"约 19GB""几千只"）、单次日志里的瞬时读数（那是证据正文，不是结论）。
>
> 依据 `AGENTS.md` R2「硬数字只能引用不能手抄」+ `reports/133` §7 升级条款（2026-11-18 已触发并落地，
> 见 `reports/140` §2.3）。

## 为什么要有这道工序

2026-11-18 一天之内同一个数字错了三次、且**同时错在三个地方**：

| 事故 | 表现 | 根因 |
|---|---|---|
| `432,343` | STATUS + KB + reports/139 三处同错，下一提交才更正为 `432,523` | 一个数字手抄三遍，没有单一来源 |
| `79 期` | 实为 **86** 期，写在"自审已收口"的条目里 | 数字是凭印象写的，没有查询 |
| `5,666 只` | 实为 **5,934** 只 | 同上 |

共同的失效机制：**数字的正确性从来没有执行器**（`reports/140` §3.1：14 条规则里 43% 纯靠自觉，
而"数字对不对"是其中唯一完全无自动化的一类）。人抄一遍、抄两遍、抄三遍，错一次就错一片；
改的时候又只改一处，于是留下自相矛盾的文档 —— 这比没写更糟，因为读者无法判断哪份可信。

## 步骤

### 1. 先判定：这个数字能不能复算？

- **能复算**（一条 SQL / 一个 `wc -l` / 一次 `git rev-list --count` 能得到）→ 走步骤 2。
- **不能复算**（外部标杆、人工判定、历史估值）→ **不要给精确数**。写"约/量级 + 口径 + 取样方式"，
  并在正文注明"不可复算"。给精确到个位的数会让人以为它可靠。

### 2. 写进证据 JSON（单一来源）

放 `docs/evidence/`，文件名带日期；结构至少含四要素：

```json
{
  "generated_at": "2026-11-18T22:40:00+08:00",
  "generator": "scripts/<生成脚本或 'manual:SQL'>",
  "facts": {
    "institution_holdings.rows": {
      "value": 432523,
      "unit": "rows",
      "query": "SELECT COUNT(*) FROM institution_holdings",
      "verified_at": "2026-11-18"
    }
  }
}
```

硬要求：

- ✅ `query` / `generator` 必须是**别人能照着跑一遍**的东西，不是"我查过了"。
- ✅ 带时区的时间戳（`+08:00`），不要裸 `datetime.now()`（`AGENTS R5`）。
- ✅ 只增不改：数字变了就新增一条带新日期的记录，旧记录保留 —— 否则你抹掉了"曾经错过"的证据。

### 3. 正文只写引用，不写数字

```markdown
| 机构持仓 | 行数见 `docs/evidence/evidence-facts-2026-11-18.json#institution_holdings.rows` |
```

如果可读性要求正文必须出现数字（如摘要行），则**数字必须与该 JSON 同源生成**
（脚本渲染、或复制后立刻用步骤 4 校验），并且同一数字**全仓只允许一处**。

### 4. 提交前跑一致性检查

```bash
uv run --locked python scripts/check_rework_guards.py
```

RG6–RG9 会挡住编号重复 / front-matter 非法 / supersede 不闭合 / 真相源引用作废结论 / 测试资产未入库。
**但它不校验数字本身**（自然语言里的数字误报率极高，`reports/133` §7 已明确否决静态检查这条路）。
所以数字这一步靠本 Skill 的"同源生成"，而不是靠门禁兜底。

### 5. 数字被推翻时

- ❌ 不要静默改掉旧数字。那会让人以为它一直是新值。
- ✅ 新报告 `supersedes` 旧报告，旧报告 front-matter 标 `superseded` + `superseded-by`
  （RG7 会检查这个闭环）。更正记录写进新报告的一节"更正"，列「旧值 → 新值 → 为什么错 → 怎么发现的」。
- ✅ 如果同一数字散落在 N 处，**一次性全部改完并在报告里列出改了哪几处**。
  `432,343` 那次就是因为只改了 STATUS，KB 和 reports/139 还留着旧值。

## 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 报告里写"共 5,666 只" | 无法追溯、无法纠错 | 写引用 + 证据 JSON |
| 把上一份报告的数字抄进新报告 | 一处错传三代 | 重新查一遍，或引用同一证据 |
| 用" aproximadamente / 约"包装精确数 | 既不可复算又显得权威 | 要么给可复算的数，要么真给区间 |
| 数字刷了但 `last-reviewed` 没动 | 读者以为复核过 | 一并更新 |
| 只改一份文档 | 文档间自相矛盾 | 全仓 grep 该数字，一次改全 |

## 检查清单（复制到报告末尾）

- [ ] 每个精确数字都能追到 `docs/evidence/*.json` 的一条 `query`/`generator`
- [ ] 同一数字全仓只出现一处（或全部同源生成）
- [ ] 不可复算的数字已降级为"约/量级 + 口径"
- [ ] `uv run --locked python scripts/check_rework_guards.py` 通过
- [ ] 若推翻了旧数字：旧报告已标 `superseded`，更正记录已写
