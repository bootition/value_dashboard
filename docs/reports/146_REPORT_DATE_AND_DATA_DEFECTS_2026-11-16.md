### 1.1 事实

**8 张表**存在 `report_date = YYYY-01-01` 的行，全部来自**同一个 CSMAR 批次**
`8c165b0a81c24728ae58f38b38f0ff7b`（`fetch_time = 2026-09-18`，单日单批）：

| 表 | 01-01 行数 | 占比 | 有上一年 12-31 对应 |
|---|---|---|---|
| `csmar_balance_items` | 71,858 | 20.1% | 100% |
| `report_metadata` | 71,860 | 20.1% | 100% |
| `csmar_income_items` | 71,525 | 19.5% | 99.9% |
| `cash_flow_activity` | 62,370 | 17.0% | 99.9% |
| `cash_flow_indirect` | 62,369 | 25.5% | 99.8% |
| `csmar_cashflow_items` | 62,367 | 18.4% | 99.9% |
| `csmar_financial_items` | 45,725 | 19.7% | 98.8% |
| `financial_sector_items` | 1,014 | 17.9% | 100% |
| **合计** | **449,088** | | |

### 1.2 方向证明（三重独立证据）

**① 与上一财年 12-31 逐值对比**（`cash_flow_indirect`，三列：净利润 / 固定资产折旧 / 间接法经营现金流）

| 对比对象 | 可配对 | 三列全同 |
|---|---|---|
| **上一财年** 12-31 | 58,022 | **46,995（81.0%）** |
| **同年** 12-31 | 62,267 | **0（0%）** |

→ 是**上一年年报的副本**，不是当年数据。

**② 个案**：`600519` 的 `2023-12-31` 与 `2024-01-01` 两行 —— 净利润均
77,521,476,277.8、经营现金流均 66,593,247,721.09、折旧均 1,651,428,992.2、
期初现金均 152,378,738,982.83，**完全一致**。

**③ `report_type` 全被标成 `'quarterly'`**，但数值形态是年报 —— 说明日期解析时
把年报错记成了次年年初，类型也跟着错。

### 1.3 危害

| 危害 | 说明 |
|---|---|
| 伪期次 | 任何 `ORDER BY report_date` 的「最近一期」会把 `2024-01-01` 当成新年度期次 |
| 财务序列错 | LAG / 环比 / TTM 多出一个期次，区间算错 |
| 覆盖率失真 | 期次统计与覆盖率被重复计数 |
| 行数虚高 | `cash_flow_indirect` 有 **25.5%** 是这类行 |

### 1.4 修法（`scripts/repair_nonstandard_report_dates.py`）

新增模块 `app/core/report_periods.py`（**单一实现，写库守卫与修复脚本共用**）：

- `is_standard_report_date()` —— 合法报告期只有 03-31 / 06-30 / 09-30 / 12-31
- `report_period_name()` —— 报告期 → 中文口径名（2026 半年报）
- `canonical_year_start_target()` —— `YYYY-01-01` → `(YYYY-1)-12-31`

修复脚本的保守规则：

| 情形 | 动作 | 理由 |
|---|---|---|
| `YYYY-01-01` 且 `(YYYY-1)-12-31` **已存在** | **删除** | 同一份数据已有正确期次的副本 |
| `YYYY-01-01` 且 `(YYYY-1)-12-31` **不存在** | **改期** | 该期唯一副本，语义明确 |
| 其它非标准期 | 只报告，不动 | 语义不明，交人工 |

改期后**强制重算 `report_type`**（`2008-01-01` 原标 `quarterly`，改期后应为 `annual`）。

**全库 dry-run 实测**：

```
合计：可删重复 418,455 行，可改期 30,633 行，待人工 0 行
```

### 1.5 安全约束

- 默认 **dry-run**；写库必须 `--apply --confirm-write` 双开关
- 写库路径**强制走** `DatabasePathSet.from_env()`（worktree 里会因 run_root 校验失败而拒绝）
- 写库走 `exclusive_update()` 单写者锁
- dry-run 允许 `--db-path` 直连只读库（worktree 没有 `data/`）

### 1.6 写库守卫（防复发）

`SupplementFetcher._persist_rows()` 新增 `_drop_nonstandard_periods()`：
落库前丢弃 `report_date` 非标准期末的行，计数量挂
`last_dropped_nonstandard_periods` / `last_dropped_nonstandard_sample`。

丢弃而非抛错：一次补采里个别行日期畸形不该让整批失败。

## 3. 季报 EBITDA：一次结论反复，最终判定「数据源确实没有」

### 3.1 Agent 提出的反驳

`date-anomaly-scan` 报告称「**一季报/三季报不披露补充资料」不成立**，
依据是按 source 拆开后 CSMAR 的 03-31 覆盖率 98.09%、09-30 99.68%。

### 3.2 主控复核：那是**小分母百分比假象**

| 报表期 | `cash_flow_interdirect` 行数 | 有折旧摊销 | 占上市 5,580 家 |
|---|---|---|---|
| 2023-03-31 | **33** | 33 | **0.6%** |
| 2023-06-30 | 5,364 | 5,360 | 96.1% |
| 2023-09-30 | **13** | 13 | **0.2%** |
| 2023-12-31 | 5,440 | 5,436 | 97.4% |
| 2024-03-31 | **2** | 2 | **0.0%** |
| 2025-03-31 | **2** | 2 | **0.0%** |

CSMAR 的 03-31 行合计 5,823 行覆盖 **24 个年份**，平均每期 **242.6 只**
（对 5,500+ 家上市公司）。所谓「98%」是「CSMAR 那 33 行里有 33 行有值」——
**分母是 33，不是全市场**。

### 3.3 最终判定

**原结论成立**：A 股一季报 / 三季报绝大多数不披露现金流量表补充资料（间接法），
因此折旧摊销拿不到，EBITDA 算不出来。少量有值的是自愿披露或部分覆盖。

**结论：季报 EBITDA 修不了**（用户已明确「修不了，季报没有这个数据，那也就罢了」）。
现状处理（`reports/145`，另一分支）已是最诚实的做法：**按字段回溯到最近可算期
（半年报/年报），并在界面标注「2026 半年报口径」**。

### 3.4 可修的部分

`2025-06-30` 的 cfi/cfa 只有 5 行是**真断档**（不是披露规则问题，同期三表都正常），
重采该期即可补齐。这条已登记为后续动作，本次不改（需网络 + 写正式库，按 W4 由主控串行执行）。

## 5. 本次修的：`roce_eligible` 不再留 NULL

### 5.1 问题

`SNAPSHOT_UPDATE_SQL` 的聚合**左表是 `roce_history`**。没有 ROCE 历史的股票
（新股 / 金融股 / 年报不足 1 期）在聚合里没有行，`UPDATE ... FROM` 就碰不到它们，
`roce_eligible` 停在 `INSERT` 时的 **NULL**。

**后果不是"少个标记"，而是双向漏筛**：
`WHERE roce_eligible` 和 `WHERE NOT roce_eligible` **都不命中**这些股票 ——
用户按「非金融·市值≥100亿·有效年数≥5」筛选时会**静默漏掉公司**。

### 5.2 修法

聚合左表改为 `indicator_snapshot`，`LEFT JOIN` ROCE 聚合，
`n5/n10/n20` 用 `COALESCE(..., 0)` → 无历史时 `eligible` 自然算出 `false`。

### 5.3 测试

`tests/regression/test_roce.py` 新增
`test_eligible_is_false_not_null_without_roce_history`：只建快照、不建任何
`roce_history`，断言 `roce_eligible is False`（不是 NULL）。
