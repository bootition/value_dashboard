## 一、先回答"有没有拿全盘搜索找工作区文件"

**没有。** 这次会话里没有跑过 `find /`、`dir C:\`、`where /r` 这类全盘命令。
所有文件定位都是仓库相对路径（`grep -n ... app/core/...`、`ls tests/regression/`）。

但**存在三个同构的浪费**，本质相同：拿"大范围扫描"去解决"小范围问题"。

| 同构浪费 | 实例 | 代价 |
|---|---|---|
| 用**全表扫描**代替定点查询 | 反复对 `balance_sheet`（14.4 万行）、`raw_response_archive_all`（含 payload，读全部二进制算哈希）做聚合 | 归档哈希校验一次要读 3.4 万条 payload，几十秒级；我为了同一件事跑了 3 次 |
| 用**全量 S1** 代替定向测试 | 改动只碰了 4 个文件，却跑了两次全量 `tests/regression`（1,542s + 1,877s） | 合计 **57 分钟**，两次都失败，且两次的失败原因都与改动无关（并发重命名 / 测试桩签名） |
| 用**原始行 dump** 代替聚合 | 排查成交量量纲时 `SELECT ... FROM price_daily_raw ...` 没加 `LIMIT`，一次吐出 14KB 原始行 | 输出被截断到 spill 文件，关键信息淹没，等于白跑一次 |

**替代做法**：
- 查证类查询一律先 `COUNT(*) GROUP BY 桶`，需要样本时 `LIMIT 10`；
- 改动 <5 个文件时先跑定向用例，全量 S1 只在**合并前**跑一次；
- 全表要扫时，先想"能不能用索引列/主键把它缩成一个区间"。

## 二、时间到底花在哪（实测）

| 项目 | 实测 | 说明 |
|---|---|---|
| **纯 `sleep` 等待** | **≈2.5 小时** | 用了 `sleep 420/600/720/900/1700` 共十余次。这是最大单项 |
| 全量 S1 ×2 | 57 分钟 | 见上 |
| 单次 python 进程启动 | 151 ms（裸）/ 250 ms（导入 duckdb）/ 567 ms（导入 calculator） | **不是瓶颈**，别再为这个优化 |
| 开 DB + 一次聚合 | 329 ms | 同上，不是瓶颈 |

**结论：慢的不是工具调用，是我把"等"当成了工作方式。**

我用的模式是「起后台任务 → `sleep N` → `tail 日志`」，
而项目里本来就有 `job_list` / `job_output(wait=true)` 这套后台作业工具。
`sleep 1700` 这 28 分钟里我什么都做不了；`job_output` 可以设 `timeout_ms` 阻塞等待，
期间到点就返回，且能拿到结构化输出而不是去 `grep` 日志。

## 三、真正把任务拖长的四件事

### 1. 编辑方式选错（**最高频的返工源**）
用 `python - <<'PYEOF'` + `assert old in s` 做文本替换，结果：
- 三次替换**静默没生效**（`sed`/`grep` 模式没匹配上，但我没校验返回值）；
- 两次因为控制台编码（GBK）把中文注释写成 mojibake，直接 `SyntaxError`；
- 一次在替换字符串里写了真实换行，把文件写成语法错误（29 个 ruff 报错），
  又得回头读文件、重写整块。

每次失败都是「读文件 → 改 → 发现没生效 → 再读 → 再改」一整圈。
**替代**：用带**精确字面量匹配**的编辑工具（不匹配就报错，不会静默通过）；
需要批量生成内容时，先写到临时文件再检查，不要内联 heredoc 拼 SQL/中文。

### 2. 数据修复脚本的判据设计错了，导致要修两轮
`repair_star_volume_x100.py` 用「断点前后 20 行成交量中位数之比」判单位错。
这个判据在**前窗本身已被污染**时失效，于是：
- 第一轮修了 616 只，漏了 688565–688569（每只前 20 行里 10 行已污染）；
- 还漏了 688139（整段 1,631 行历史 ×100，不属于"断点之后"）；
- 同时 qfq 侧 225 只 / 87,407 行的 ×100 完全没被发现。

**教训：判据要建立在"不会说谎的恒等式"上，而不是"看起来像"的统计量。**
成交额恒等式 `turnover ≈ volume × close` 是硬约束；中位数比值只是启发式。
换成硬判据后，一次就定位到全部范围（`scripts/repair_star_volume_rows.py`）。

### 3. 自伤：重启 Web 服务把数据库锁住，挡住了正在干活的 agent
发生了两次。DuckDB 单写者锁：Web 服务一起来就独占文件，
所有审计/修复 agent 的只读连接全部失败。
**替代**：agent 在跑时不要动服务；需要验证接口时用临时库起临时实例。

### 4. 假读数（同一个坑踩了三遍）
- `ExtendedIndicatorBuilder.build()` 的 `rows_written` 报 0 或 36 万（都是假的）；
- 我自己新写的修复脚本又一次用了 `.rowcount`，DuckDB 对 `UPDATE` 返回 **−1**；
- 一次性脚本里的"防误伤"SQL 条件自相矛盾（同时 `<> '保险II'` 和 `= '保险II'`），恒返回 0。

**替代**：任何"修了多少行"都必须是**修前按同一谓词数一遍 + 修后终检**，
不能拿驱动返回的 rowcount 当证据。

## 四、派出去的 agent 为什么会空转两小时

`fix-star-volume-remain` 这个 agent 的任务书本身是清楚的（5 条残留 + 判据），
但它**两个多小时一个字都没落盘**（三个目标文件时间戳停在启动之前）。
复盘暴露的问题在**我这一侧**：

1. **任务书给了"先验证再动手"的暗示却没有时间盒。**
   我写了"建议把正式库 copy 到临时目录跑（彩排）"——
   28GB 的库 copy 一次就是几十分钟，它很可能卡在这类前置动作上。
   对"改动明确"的任务，应该要求**先落一版能跑的代码，再彩排**。

2. **没有要求中途汇报。** 派出后我一直在 `sleep` 等它，
   直到用户问起才去查它的文件时间戳。应该派出去后就约定"每 20 分钟一次进度"。

3. **它拿到的判据是我错的那一版。** 我给的是旧脚本的"前窗中位数"思路，
   而这个思路本身在污染数据上失效——它大概率在反复尝试让它工作。
   **判据错了，派再多 agent 也修不出来。**

4. **没有失败退出条件。** 任务书里没有"做不完就交半成品 + 说清卡点"，
   于是一直不出声地跑。

**替代规则**（已写入任务书模板建议）：
- 派 agent 必须给**时间盒**（"最多 30 分钟"）和**硬性落盘要求**（"每完成一个文件就存"）；
- 必须给**失败路径**（"做不完就交现状 + 卡点"）；
- 超过约定时间没有文件变更 → **中断它，自己做**，不要继续等；
- 判据类任务由主控先自己用一条 SQL 验证判据成立，再派出去。
