# 数据库治理计划第二次复审

## 1. 复审结论

方向正确，但**当前仍不能直接执行**。按大厂变更管理标准，还缺三类交付物：

1. 可执行的 runbook 与自动化脚本；
2. 明确的容量预算、回滚窗口和验收基线；
3. 每项优化的原型验证与黄金对照结果。

本报告把计划收紧为“**条件批准**”：满足下列准入门槛后才能进入执行阶段。

---

## 2. 仍未解决的关键问题

### 问题 A：磁盘容量预算没有算到最坏情况

原报告只写“D 盘 183.6GB，足够”，但没有峰值预算。实际必须按最坏情况计算：

| 对象 | 估算 |
|---|---|
| 旧 DuckDB 文件保留 | 53.4GB |
| 逻辑备份/Parquet 导出 | 约 30~40GB |
| 新 DuckDB 文件 | 约 33~38GB |
| 峰值合计 | 约 **125GB** |

结论：D 盘可执行，但**禁止同时再做一份 53GB 的整文件 OS 拷贝**。
执行顺序必须是：

1. 停服；
2. 先做逻辑备份（`vd backup create` 或逐表 Parquet）；
3. 验证备份 manifest；
4. 生成新库；
5. 新库验证通过后才处理旧文件；
6. 旧文件保留至观察期结束再删除。

### 问题 B：没有“回滚窗口”定义

大厂标准要求任何数据库替换都有明确回滚条件。

必须补充：

- 新库上线后观察 **至少 1 个完整自动更新周期 + 1 次冷核对**；
- 观察期内旧文件不删除；
- 出现以下任一情况立即回滚：
  - 任一张表行数不匹配；
  - 任何主键冲突；
  - `ready=false` 或出现新 warning_codes；
  - 冷核对 OOM；
  - lineage 六项任一项非 0。
- 回滚动作：停服 → 删除新文件 → 恢复旧文件名 → 重启 → 再跑数据质量。

### 问题 C：P0 缺少可复现脚本，不能靠手工 SQL

`EXPORT DATABASE / IMPORT DATABASE` 只是方向，不是 runbook。执行前必须有：

- 自动导出脚本；
- 自动导入脚本；
- 校验脚本，逐项检查：
  - `duckdb_tables()`；
  - `duckdb_views()`；
  - `duckdb_indexes()`；
  - `duckdb_constraints()`；
  - `schema_migrations`；
  - 每张表 COUNT(*)；
  - 关键表内容指纹；
  - 两个 sequence 的 nextval 探针。
- 脚本在**临时副本**上通过后，才能用于正式库。

建议用逐表 `COPY ... TO 'xxx.parquet'` + 清单文件，而不是一次性
`EXPORT DATABASE`。原因：

- 单表失败可重跑；
- 42M 行 `source_audit` 和 17M 行价格表可以单独观察进度；
- 每张表都有独立行数、字节数和 SHA-256；
- 更符合大厂“可恢复、可审计”要求。

### 问题 D：P1 lineage 优化只有方向，没有 SQL 原型

不能批准直接写正式查询。必须先在临时库交付：

- 新 hash 集合表 `raw_response_archive_valid_hash` 的 DDL；
- 与归档写路径同事务刷新的方案；
- 旧查询与新查询的对照脚本；
- 在正式库只读连接上的基准：
  - 耗时；
  - 峰值内存；
  - 六项 lineage 计数；
  - warning_codes。
- 只有“结果全等且性能更优”才允许切换。

### 问题 E：P2 分区设计缺少工程细节

至少还要定义：

- 分区表命名：`raw_response_archive_YYYYMM`；
- 合并视图的上限：建议最多保留 **36 个**活跃分区；
- 超出上限的旧分区必须完成 Parquet 冷导出后从 DuckDB 删除；
- 分区清单表结构，写入 SQLite；
- 轮转事务与写路径的锁顺序；
- Parquet 冷归档目录布局与 manifest 格式；
- 冷归档恢复 CLI 的验收用例。

### 问题 F：P3 黄金数据集没有定义

“黄金对照”不能临时抓几只股票。必须冻结：

- 至少 200 只代表性股票：
  - 正常股票；
  - 银行/券商（监管字段特殊）；
  - B 股；
  - 停牌股；
  - 新股；
  - 无分红股；
  - 多次分红/送转股；
  - 国债曲线陈旧边界股票。
- 对每只股票保存当前 `build_series` 和 `_stats_for_stock` 输出；
- CI 中只允许新实现输出与黄金文件完全一致。

### 问题 G：现有备份太旧

`data/backup` 中可用的全量备份主要是 7 月产物；当前 50GB 正式库
没有对应新基线。执行 P0 前必须**先完成并验证一次当前库的逻辑备份**，
否则任何失败都没有可恢复基线。

## 3. 方案是否达到最优

| 方案 | 评审 |
|---|---|
| P0 离线重建 | 方向最优；执行方式改为**逐表 Parquet + 清单 + 脚本化** |
| P1 lineage hash 集 | 方向正确；建议做成与写事务同刷新的物化 hash 表 |
| P2 日历月分区 | 正确；补充 36 分区上限、冷导出、清单与恢复 |
| P3 批量取数 | 正确；冻结黄金数据集，SQL 计算下推继续暂缓 |
| P5 可观测性 | 不足：还要记录每次更新的步骤耗时、内存峰值、文件大小、WAL |
| P6 备份演练 | 必须提前到 P0 之前，且要实际恢复一次并抽样验证 |

## 4. 最终执行门禁（Go / No-Go）

只有以下全部为“是”，才允许执行 P0：

- [ ] 当前库逻辑备份已完成且 manifest 校验通过；
- [ ] 备份恢复演练已在临时目录成功；
- [ ] 导出/导入脚本已在临时副本全绿；
- [ ] 行数/视图/索引/约束/sequence 校验脚本就绪；
- [ ] 磁盘峰值预算 ≤ 160GB 已确认；
- [ ] 回滚窗口与触发条件已书面确认；
- [ ] 服务停服命令与恢复命令已演练；
- [ ] 用户已确认维护窗口。

任何一项不满足，P0 不得执行。
