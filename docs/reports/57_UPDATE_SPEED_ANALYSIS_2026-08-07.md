# 自动更新速率剖析与限速调整报告（2026-08-07）

## 1. 现象与实测

当前正式自动更新 job（2026-08-07 18:02 启动）逐股价格处理实测：

- 该 job 至 19:52 完成 577 / 5372 只，耗时约 6600s → **约 11.4s/股**。
- 按此速率全量需约 **17 小时**，明显偏慢。

从运行日志（该 job 2365 个请求间隔）细化：

| 指标 | 值 |
|---|---|
| 请求间隔中位数 | ~1.0s |
| 间隔 p90 | ~2.0s |
| 间隔 >60s | 43 次（最长 220s，集中于 ~90-100s） |
| 间隔 5-60s | ~104 次 |

结论：**正常单次抓取约 1s（不慢）**；拖慢整体的是 **43 次 ~90 秒的尾部惩罚**。这类 90s 模式与 baostock 服务端对高频请求的限流/延迟响应一致（请求最终“成功返回”，socket 未超时）。

## 2. 根因

价格抓取每次请求前等待 `rate_limit_interval`，baostock 配置为 **0.1s（10 请求/秒）**，远超免费源服务端耐受度，触发限流惩罚——表现为每 N 次请求后插入一次约 90s 服务端等待。

## 3. 调整（默认限速降低，配置可覆盖）

- `config/default.yaml` 与 `Manager.DEFAULT_ADAPTER_RATE_LIMITS`：`baostock: 0.1 → 0.8`（约 1.25 请求/秒）。
- 预期效果：惩罚显著减少，稳定速率约 2.5–3.5s/股（每股 raw+qfq 两次请求 ~1.6s + 网络 ~1s），全量约 4–6 小时，优于当前约 17 小时。
- 用户可按需在 `config/user.yaml` 的 `adapters.rate_limit_interval.baostock` 覆盖（如带宽充足可下调，谨慎触发惩罚）。

## 4. 说明与后续建议

- 本次调整对**下次启动的自动更新**生效；当前正在运行的 job 保持原速率继续。
- 进一步提速方向（未在本轮实施）：
  1. 请求级超时兜底：包装线程 45s 超时放弃并记重试，把偶发长尾压到上限；
  2. 并发价格抓取（网络请求并发、DB 写串行），需评估 bao securitystack 会话线程安全；
  3. 换用 tencent/tdx 作为价格主源（HTTP、可并发），baostock 兜底。

## 5. 验证

- 适配器相关回归 8/8（含限速应用契约、会话恢复）；Ruff（app+tests/regression）全绿。
- 调参属配置层面，未触碰自动化更新契约。
