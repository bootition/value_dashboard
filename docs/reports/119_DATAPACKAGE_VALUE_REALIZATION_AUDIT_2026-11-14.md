# 2026-11-14 数据包价值兑现度审查

> 详细版（含逐表数据与复现脚本）：`.planning/2026-11-14-datapackage-review/REPORT.md`
> 审查方式：**全程只读**（DuckDB `read_only=True`、SQLite `mode=ro`、纯文本检索），未写库、未改代码。

## 1. 结论（TL;DR）

1. **"搬进来"已经完成，"用起来"只完成一半，且有一半正在腐化。**
   CSMAR C17 的 845 个字段 100% 入库（去变体后 17 表 / 474 数据列 / 462 万行），但真正进入运行时代码的只有 **34 列（7.2%）**；我们导出的 VD 数据包 31 表 / 1.52 GB 依赖链闭合，但其中 **6 张表在 2026-09-20 导出后就没再更新过**。
2. **发现 1 个 P0：`indicator_ext` 冻结在 2026-06-30，而快照已到 2026-09-30 → 界面上 55 项扩展筛选指标当前全部是"能选中但筛不出结果"的死条件。**
   实测：与快照按报告期 join 后**只有 3 只股票有值**；条件 `free_cash_flow > 10 亿` 返回 **0 只**。
3. **衍生数据没有续跑机制是系统性疾病**：`indicator_ext`、折旧摊销/资本支出补采、扣非净利润补丁、金融监管指标、ETF 行情、PDF 域共 6 条链路都是"一次性脚本/CLI"，不在自动更新主流程里。
4. **抓取侧也有自己的断供**：扣非净利润 2026Q2 起归零（Q3 = 0 行）、2026Q3 固定资产只剩 1.8%（Q2 为 99.9%）、ETF 行情落后 57 天、`roic` 因"应付债券缺失即整列 NULL"塌到 11.8%。
5. **CSMAR 原始包里还有没榨的部分**：`Indcd/Indnme`（行业变更历史）、`IfCorrect/DeclareDate`（差错更正）、`Typrep`（报表类型）**在导入时被丢掉**，恰好对应 STATUS 明列的两个能力缺口——不用再抓数，重跑导入即可。

### 2.1 P0 证据：55 项扩展指标的死条件

```sql
-- join 后非空只有 3 只
SELECT count(e.stock_code) FROM indicator_snapshot s
LEFT JOIN indicator_ext e ON e.stock_code=s.stock_code AND e.report_date=s.report_date;   -- 3
-- 任取一个业务条件：0 结果
... WHERE e.free_cash_flow > 1e9;   -- 0
```

根因：`ExtendedIndicatorBuilder` 只被 `vd data compute-extended-indicators` 与测试调用，
`app/core/update.py::_run_incremental_update_flow` **没有这一步**；2026Q3 财报 10 月就绪后无人触发重建。

## 5. 我们抓取的内容能补什么（结论）

- **补时效**：CSMAR 止于 2025-03-31；我们三表到 2026-09-30、行情到 2026-11-13、国债到 2026-11-13。这条已经在自动链里，是核心资产。
- **补结构**：CSMAR 完全没有的 12 类域（行情/除权/股本变动/分红事件/融资/回购/主营构成/公告/国债/指数/估值/ETF）我们都有。
- **补口径**：CSMAR "市值A 含负债"的坑，我们用「报告期收盘价 × 当时股本」自算绕开。
- **还没补上的（抓取侧自己的欠账）**：扣非、折旧摊销/资本支出、监管指标、ETF、Q3 固定资产——全部是"有源、没调度"，不是"没有源"。
- **不用抓就能补的**：行业变更历史与差错更正标记就在 CSMAR 原始文件里，重导即可。

## 6. 建议顺序

R1 重建 ext + 补采 → R2 ext 接入自动更新（季度门控）→ R3 ETF 进主流程 → R4 `interest_bearing_debt` 口径 → R5 技术指标重算触发 → R6 三条手工链接进自动更新 → R7 CSMAR 元数据重导 → R8 两张零引用表兑现 → R9 数据包重导出 + 文档纠偏。

**纪律建议**：任何派生表必须登记 `refresh_owner`（自动/手工）与 `stale_after_days`，并在 `vd data status` 暴露"最新报告期 vs 快照报告期"差值；差值 >0 即 P1。
