# 数据库与主机现状调研及下一步优化方案

## 1. 调研结论

正式库与主机现状可以概括为：

1. **功能与数据质量正常**：readiness=true、warning_codes=[]、lineage
   六项缺口为 0，核心数据完整。
2. **DuckDB 文件存在约 16.3GiB 可回收高水位**：文件 49.7GiB，实际有效
   块约 33.4GiB。这是下一步最大、最安全的优化目标。
3. **主机具备离线重建条件**：12 核 24 线程、32GB 内存、NVMe SSD，
   D 盘当前剩余 183.6GB，足以同时保留备份、旧文件和新文件。
4. **归档冷热分层已生效**：历史 BLOB 26.1GB 已隔离在
   `raw_response_archive_history`，active 热表 2.7GB，写入不再触发
   26GB 大表整表校验。
5. **统计域指纹已稳定**：无真实输入变化时，5553 只统计域会跳过，
   不再每次启动重建。

## 4. 内存观察

- 更新阶段内存稳定在约 0.3~1.1GB。
- 冷核对期间峰值约 13~16GB，受 `memory_limit=14GB` 约束。
- 更新结束后，进程 WS 仍会间歇回到 5~14.7GB；但同一时刻
  `pragma_database_size()` 报告的 DuckDB memory_usage 只有 9.2MiB。
  说明这不是查询在消耗内存，而是进程保留的堆页/文件映射页未及时归还
  Windows；当系统空闲内存降到约 2.5GB 时，OS 会把 WS 压回约 5GB。
  属于“不优雅但不失控”，建议加入监控并在重建数据库后重新评估。

## 5. 推荐方案与优先级

### P0：DuckDB 离线重建（收益最确定，先做）

- 目标：把 49.7GiB 文件中约 16.3GiB 空洞物理回收。
- 前置条件已满足：D 盘剩余 183.6GB。
- 预期收益：
  - 文件降到约 33~38GiB；
  - 冷核对、统计域、筛选就绪核对扫描量下降；
  - 可能把 `memory_limit` 从 14GB 进一步下调。
- 风险：需要停机窗口、严格校验；预计耗时 1~3 小时（SSD）。
- 实施顺序：
  1. 停服务并做一次现有 12GB backup 之外的 DuckDB 冷备份；
  2. 新库逐表导出/导入（保留 schema、索引、视图、sequence）；
  3. 校验每表行数、关键表内容哈希、schema 版本；
  4. 原子替换文件并重启；
  5. 记录重建前后冷核对耗时、内存峰值、统计域耗时。

### P1：lineage 冷核对查询优化（内存方向三）

- 目标：避免 42M 行 `source_audit` 在 readiness 检查中与 26GB BLOB
  域直接 join。
- 做法：
  1. 先物化“有效归档 hash 集合”（只含 hash，无 payload）；
  2. lineage 缺口改用半连接/反连接；
  3. payload 长度检查下推到少量候选行；
  4. 与归档写路径联动刷新 hash 集合。
- 验收：优化前后 `build_data_quality_status` 的 lineage 结果必须完全
  一致，且冷核对峰值/耗时下降。

### P2：原始归档自动轮转与冷导出

- 目标：防止 active 热表再次涨成 26GB 级大表。
- 规则：active 行数或字节数超过阈值（建议 20GB 或 50 万行）时：
  1. 自动把 active 改名为下一段 history；
  2. 新建空 active；
  3. 旧 history 的 BLOB 可选导出 Parquet 冷归档并保留 hash 元数据。
- 这样把当前一次性修复变成长期机制。

### P3：统计域批量取数试点（速度方向）

- 先做低风险版本：SQL 一次取 200~500 只股票的输入，Python 保持现有
  计算口径。
- 用当前 5553 只全量结果做黄金对照；完全一致后再考虑把分位聚合继续
  下推 SQL。
- 预期：全量统计域从约 9~10 分钟降至 3~5 分钟。

### P4：价格源与并发再校准（最后做）

- 当前 2 req/s 与并发上限是防封禁红线；只允许在重建完成后，用可控
  样本做有界探测并回写证据，不建议直接放宽。
