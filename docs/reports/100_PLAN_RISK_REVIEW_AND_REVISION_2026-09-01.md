# 数据库治理计划风险复审与修订

## 1. 复审结论

`reports/99` 的调研事实继续有效；其执行计划按大厂变更管理标准复审后
做如下修订：

1. P0 离线重建仍为第一优先，但增加强制预演与序列/索引/视图验证。
2. P2 归档自动轮转条件由“20GB 或 50 万行”改为“**日历月分区 + 更低的
   硬阈值**”，并明确：同一 DuckDB 文件内轮转不回收磁盘，必须配套
   冷导出与周期性重建。
3. P3 统计域批量化范围收窄为“**先批量取数，SQL 不参与指标口径计算**”。
4. 新增 P5 可观测性与内存基线、P6 备份恢复演练，作为前置保障。

## 2. 对原计划逐项复审

### P0：DuckDB 离线重建——批准，但必须先做小规模预演

大厂标准要求任何不可逆数据库替换必须先证明“可重建、可校验、可回滚”。

修订后的步骤：

1. 在临时测试库演练 `EXPORT DATABASE / IMPORT DATABASE`，验证：
   - 表、主键、索引、视图全部恢复；
   - `raw_response_archive_all` 视图依赖完整；
   - `schema_migrations` 版本正确；
   - `fetch_batch_id_seq` / `source_audit_id_seq` 导入后 nextval 不重复。
2. 在正式库上先执行只读 `EXPORT DATABASE` 到 D 盘临时目录；
3. 将导出的 Parquet 导入一个临时新库，不替换正式文件；
4. 对新库逐表比对行数、关键表内容哈希、view/constraint/index 清单；
5. 全绿后才安排停机替换。

验收线：所有行数与哈希一致，且新库插入一行后主键序列不冲突。

### P1：lineage 查询优化——批准，但必须做“红蓝结果对照”

- 不允许直接改写正式数据质量 SQL 后上线；
- 先在只读副本/临时连接上同时运行旧查询与新查询；
- 新查询必须满足：
  - 旧 `warning_codes` 与新 `warning_codes` 完全一致；
  - 六个 lineage 计数完全一致；
  - 内存峰值和耗时下降才替换。
- 如果任何一行结果不一致，停止切换，回退旧查询。

### P2：原始归档自动轮转——原阈值不合适

原计划“20GB 或 50 万行”有两个问题：

1. **20GB 已经太晚**。本次历史表 26GB 时单行提交峰值达 24.5GB。
   不能等热表再次接近这个体量。
2. **行数不是可靠的代理指标**。BLOB 大小差异大：active 热表
   3,541 行已经是 2.7GB；历史上 2026-08-31 单日写入约 19GB。

修订为**双重机制**：

- **日历月分区**：每月一个 `raw_response_archive_YYYYMM` 分区；
  当前月 active 保持小表，月底自动关闭并新建下月表。
- **硬阈值提前触发**：任一条件满足即轮转：
  - 字节数 ≥ 5GB；
  - 行数 ≥ 100,000；
  - 分区年龄 ≥ 31 天。
- 轮转必须在单写者锁内原子完成：
  1. 建新表；
  2. 重建 `raw_response_archive_all` 视图；
  3. 旧分区标记为只读；
  4. 记录分区清单到 SQLite 元数据表。
- 正式启用前，先做一次“表大小与提交成本”校准：用探测表写入
  1GB/2GB/4GB BLOB，测量提交耗时和峰值，确定安全阈值，不得想当然。

**重要认知**：DuckDB 文件内建多个表并不会自动缩小物理文件。轮转只能
阻止“单表过大导致提交扫描”，磁盘回收仍需配合 Parquet 冷导出 + P0 重建。

### P3：统计域批量取数——批准范围缩小，SQL 暂不参与计算

原计划中“最终把分位统计下推 SQL”风险过高，暂时冻结。

修订为两阶段：

- **阶段 A（本次批准）**：SQL 只做批量取数。
  - 一次查询 200~500 只股票的 raw 价格/财务/股本/分红；
  - Python 保留现有 `build_series` / `_stats_for_stock` 全部口径；
  - 输出与当前逐股查询做全量黄金对照。
- **阶段 B（暂缓）**：只有阶段 A 稳定且收益达标，再评估把
  `COUNT/SUM/percentile` 等纯聚合下推 SQL。

必须遵守的 SQL 安全规则：

- 禁止一次 join 全市场多年价格；按股票代码分块；
- 每块执行前 `EXPLAIN` 并记录内存；
- 设置 `preserve_insertion_order=false`，临时目录指向 D 盘；
- 所有窗口对齐保留 Python 原有边界条件：
  - TTM 年报直取 / 季报差分；
  - 股本 step 函数；
  - 分红 announcement_date ≤ ex_date 与 12 个月滑窗；
  - 国债曲线 ≤5 日陈旧限制；
  - NaN/None 处理一致。
- CI 增加“统计域黄金样本”回归，禁止无对照修改。

### P4：价格源再校准——维持最后，红线不变

不做变更。只有 P0/P1/P2 完成且长期监控稳定后，才允许有界探测。

## 3. 新发现的风险与对策

| 编号 | 风险 | 对策 |
|---|---|---|
| R1 | 重建过程数据损坏 | 冷备份 + 临时新库验证 + 哈希清单 + 保留旧文件直到观察期结束 |
| R2 | IMPORT 后 sequence 回退导致主键冲突 | 临时库已验证；正式导入后再插入一行探针，确认 nextval 大于当前 max(id) |
| R3 | 视图/索引/约束未恢复 | 新库逐项比对 `duckdb_views` / `duckdb_indexes` / `duckdb_constraints` |
| R4 | 轮转期间视图短暂失效 | 轮转放在一个 DuckDB 事务中：rename/create/view 原子提交 |
| R5 | 跨分区 hash 重复 | 写路径继续查全量视图；轮转后分区清单用于对账 |
| R6 | Parquet 冷导出损坏或丢失 | 每个分区导出后写 manifest，保存行数、字节数、SHA-256；恢复 CLI 前先验证 |
| R7 | lineage 优化漏判 | 红蓝结果对照 + fail-closed 回归测试 |
| R8 | 批量取数内存放大/OOM | 分块、EXPLAIN、14GB 上限、D 盘 temp_directory；OOM 时自动中止并回退旧实现 |
| R9 | 统计口径双重实现漂移 | 黄金样本 CI；阶段 B 冻结到阶段 A 完全稳定 |
| R10 | 服务空闲 WS 偏高 | 增加内存遥测；P0 后重新测量；必要时在更新完成时执行 `CHECKPOINT` 并显式释放连接池 |
| R11 | 备份过期不可恢复 | P6 每季度做一次“备份→临时目录恢复→抽样验证”演练 |

## 4. 其他可选方法评估

| 方案 | 是否推荐 | 理由 |
|---|---|---|
| 日历月分区表 + 合并视图 | ✅ 推荐 | 可预测、可归档、与现有冷热表思路一致 |
| 原 20GB/50 万行阈值轮转 | ❌ 取消 | 触发过晚，单表已可能再次引发高提交内存 |
| 归档 BLOB 导出 Parquet，热库存 hash+路径 | ✅ 远期推荐 | 最接近大厂“热元数据 + 冷对象存储”；改动较大，放 P2 之后 |
| 每月独立 DuckDB 文件 + ATTACH | 🟡 备选 | 磁盘回收直接，但连接配置、备份、跨库查询复杂度上升 |
| 统计全量 SQL 下推 | ❌ 暂缓 | 正确性风险高，收益未验证 |
| 放宽数据源限速 | ❌ 不做 | 风控红线，必须保持 ≤2 req/s |

## 5. 修订后的执行顺序

1. **P6**：先做一次备份恢复演练，确认现有备份真的能恢复。
2. **P0**：DuckDB 导出/导入预演 → 新库验证 → 停机替换。
3. **P5**：上线内存/文件/耗时可观测日志，建立基线。
4. **P1**：lineage hash 集合优化，红蓝对照后切换。
5. **P2**：日历月轮转 + 5GB/10万行/31天阈值；随后 Parquet 冷导出试点。
6. **P3 阶段 A**：统计域批量取数，黄金对照后切换。
7. **P3 阶段 B / P4**：视基线结果再评估，默认暂缓。

## 6. 与 reports/99 的关系

`reports/99` 的主机、数据库、数据质量调研事实继续有效；其执行计划
被本报告取代。相关结论以本报告和 `STATUS.md` 为准。
